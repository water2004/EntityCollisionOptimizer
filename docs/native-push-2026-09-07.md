# 实体批量推动（2026-09-07）

## 问题与实现

上一提交 `2cd0cb4` 已接管移动碰撞，但普通僵尸没有进入旧 native 冲量分支：资格判断只接受 `Entity.push(Entity)`，遗漏了 `LivingEntity.push(Entity)` 的睡眠检查包装。新增资格断言在修复前确实失败（`eco-push-coverage-before.log`），不是仅凭没有报错认定 native 得到了测试。

本次实现如下：

1. 查询返回全部选中候选、原版挤压计数和推动类型标记；批量复制到每维度可复用的 `PushBatch`。不逐候选读取外部内存或反复查找维度帧，也不在查询时剔除暂时重叠的目标。
2. 保留原版挤压伤害时机。随后按候选顺序处理连续的普通推动段，每段在执行前采集实时位置，一次 FFM 调用计算整段冲量。特殊原版覆写仍调用原逻辑，之后的普通段重新读取位置。
3. 普通推动包含 `LivingEntity` 的睡眠保护、双方 `noPhysics`、同根载具、载客状态及实时可推动性。先推动目标，再推动来源；来源被挤压杀死后，不会使用查询前的存活快照。
4. `isPushable` 复用既有实体/方块版本失效机制，帧开始时重置；避免每对推动重复走 `onClimbable → getInBlockState → getChunk`。睡眠缓存由 `SLEEPING_POS_ID` 数据更新失效，不以姿态猜测睡眠状态。
5. 延迟的是 `Vec3` 分配，不是浮点加法：每次推动立即按原版顺序相加、检查有限值并设置 `needsSync`。速度 getter 物化结果；有限 setter 替换待观察值，非有限 setter 保留它。帧切换和关闭也保留未观察的速度。
6. 批次池归属 `ServerLevel`，嵌套查询借用不同快照。原生临时数组不跨回调暴露；不同维度使用独立上下文和缓冲区。

没有密度分流、候选上限、推力上限或 native 失败回退；Carpet 的数量规则不变。特殊原版推动分派是不同实体的行为，不是低密度走 Java、高密度走 native。

这一步仍逐对执行精确推力公式，拥挤到全相交时仍是 O(n²)；减少的是语言边界、状态查询和对象分配，不是通过忽略实体降低复杂度。没有实现多项式/矩聚合近似。整个模组在极端高密度下仍不承诺候选迭代顺序的逐次观察与原版完全一致。

## JFR 与单模式诊断

环境为 Minecraft 26.2 / Fabric / Java 25，联合加载与 [移动碰撞记录](movement-collision-2026-09-07.md) 相同的 11 个优化模组，包括 Lithium、Carpet、ServerCore、FerriteCore、C2ME 和 Worldthreader。

1,000 只正常 AI/重力、生命一亿的僵尸，真实 1×2×1 石室，真实生存玩家持击退 II 钻石剑，每 13 tick 攻击。120 tick 预热、600 tick 测量；未开启扫描统计。

| 单模式 FFM 运行 | 平均 MSPT | 中位数 | p95 | 攻击 / 接受 / 观察到击退 |
| --- | ---: | ---: | ---: | ---: |
| 修改前 `eco-push-before-20260907` | 82.470 | 81.330 | 91.995 | 55 / 12 / 12 |
| 批量接入 `eco-push-after-20260907` | 52.085 | 51.384 | 58.363 | 55 / 11 / 11 |
| 含睡眠缓存的最终实现 `eco-push-final-20260907` | 47.113 | 46.559 | 54.083 | 55 / 11 / 11 |

最终均值比修改前低约 42.9%。这是不同进程、独立自然种群的诊断观察，不是严格配对实验，不能将全部差额或中间两次的差额确定归因于某个单独改动。

修改前的 Java 叶子样本：`Integer.<init>` 28.83%、`MemorySessionImpl.checkValidStateRaw` 17.95%、`Entity.push` 7.26%。装箱热点的实际栈主要来自 `isPushable → onClimbable → getInBlockState → getBlockState → ServerChunkCache`，经过 Worldthreader/C2ME 的包装；不能把这些装箱统称为本模组 ID 映射开销。

首次接入后，`getSleepingPos` 成为 17.24% 的叶子热点，因此再加入按数据更新失效的缓存。最终录制的主要 Java 叶子为 `PalettedContainer.get` 13.25%、缓存睡眠标记读取 12.58%、`LevelFrame.collectPushable` 9.73%、`PushBatch.applyNativeRun` 4.56%、`PushBatch.apply` 4.03%。剩余热点仍包括方块状态读取、候选快照及逐对状态访问；这些百分比是整个 JFR 录制期（包括启动和测试）的采样分布，受 JIT 内联和采样归因影响，不是方法精确耗时，也不包括全部 native CPU 时间。

## ABBA 整体收益

最终实现另进行三次独立 ABBA。每次同进程按关闭/开启/开启/关闭执行，每轮重建种群、预热 80 tick、测量 200 tick，每模式合计 400 个样本。关闭时保留全部优化模组，所以衡量的是本模组整体收益（含此前移动碰撞接管），不是本次补丁的独立收益。

| 独立运行 | 关闭均值 MSPT | 开启均值 MSPT | 均值降低 | 关闭 / 开启 p95 | 攻击 / 接受 / 击退 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `eco-push-abba-final-1` | 155.211 | 47.728 | 69.25% | 172.884 / 55.205 | 84 / 23 / 23 |
| `eco-push-abba-final-2` | 172.753 | 48.232 | 72.08% | 200.503 / 56.662 | 84 / 19 / 19 |
| `eco-push-abba-final-3` | 162.245 | 49.914 | 69.24% | 186.910 / 59.447 | 84 / 16 / 16 |

三次开启均值为 47.7–49.9 MSPT，整体收益约 69–72%。每次均重新生成自然种群，仍有工作量和系统状态波动；这不是对所有服务器或其他布局的性能保证。全部轮次都通过 1,000 只僵尸存活、实际接受攻击及击退检查，没有筛除较慢轮次。

## 行为测试

- 普通僵尸 native 资格断言；5 种速度观察对照，包括两个 setter、非法 setter、外部追加推力和挤压致死。
- 225 对 native 内核与原版 `Entity.push` 的逐位浮点比较，覆盖推力启用阈值、正负坐标方向、归一化分支；测试坐标靠近零，避免远处世界坐标吞掉相邻浮点边界。
- 4 组逐次舍入、推力抵消、溢出拒绝和非有限输入序列，包含同步标志被清除后读取速度不得重新置位。
- 嵌套批次隔离、查询后目标移动、开始下一帧时未观察速度保留；同一批次内清醒—睡眠—唤醒，与原版逐位比较。
- 既有低密度 34 个分派场景、12 个双向状态切换及 4 个连续帧，中密度 20/24 实体组；既有方块形状、移动、活塞与索引测试。
- 三维度并行交错 13,500 次查询和 4,500 次 native 批量推动，与原版逐实体速度对照，检查跨维度污染。工作线程使用无区块依赖的测试僵尸，仅用于验证并发隔离。

最终代码在纯 Fabric 和联合优化模组环境均通过全部 8 项 GameTest，包括扩展后的并发推动检查。仅 Windows x64 实机运行了测试；其他平台原生库的交叉构建不等于运行验证。

最终 `build` 通过；发行 JAR 包含 Windows/Linux/macOS x64 原生库和新的推动实现，不包含 GameTest 类或诊断 mixin。

原始日志与 JFR 位于本机 `D:\ar-profiles`，不放入 Git 或发行 JAR。复现命令见移动碰撞记录；单模式设置 `ECO_BENCHMARK_PROFILE=optimized`，ABBA 需取消该变量。
