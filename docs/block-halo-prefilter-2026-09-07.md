# 方块碰撞边缘预筛选（2026-09-07）

## 范围与原理

以 `3f2c26b` 为修改前基线。原扫描先用非空气位图找目标，读取 `BlockState` 后才检查原版扫描边缘规则。本次将相同判定前移，保留原版 z/y/x 顺序、完整候选以及上下文相关的实时形状查询，不更改推动、Carpet 上限或密度策略。

每个已建立索引的调色板持有 `short[256 * 3]` 和原有的已知行位图。三层分别表示非空气、非空气且 `hasLargeCollisionShape()`、非空气且为 `MOVING_PISTON`；相比旧 `short[256]` 增加 1,024 字节数组载荷。首次碰到一行才解码该行 16 格，未查询的 section 不分配索引。

| 方块在扫描外圈相交的轴数 | 使用的原版条件 |
| --- | --- |
| 0 | 非空气 |
| 1 | 非空气且大碰撞形状标志为真 |
| 2 | 非空气且为运动中活塞 |
| 3 | 排除角点 |

热方法根据 Y/Z 边缘等级，只读相应一层；X 边界列另外读取下一层，角点层恒为空。不将三层在每次热读取时重新打包。首次解码放在独立冷方法中，**不是按密度切换算法或失败回退**。三层都由同一调色板 `set/getAndSet` 写入入口维护；网络反序列化失效，复制容器不共享索引。生产 Mixin 入口没有增加。

只保存方块状态固有的筛选标志，不保存碰撞箱，也不缓存 `CollisionContext`。即使方块状态不变，活塞方块实体的进度、玩家装备、姿态和流体上下文仍会影响当次的原版形状查询。

最终相邻的 A2/C1/C2/A3 对照：A 平均 60.421 MSPT，C 平均 59.114，差额约 1.307 MSPT（2.2%）。这是当前少量样本中的小幅改善，不是稳定收益率承诺。所有有效性能运行均攻击 55 次、600 tick 后仍有 1,000 存活僵尸，完成全部 21 项测试并以退出码 0 结束；没有手动结束的结果混入。

## 测量边界

各轮场景相同但种群随机演化、GameTest 位置与有效击退数量不同，不是逐 tick 完全相同的输入。Java 叶子行号只代表 JIT 采样归属，不是指令计时；报告同时使用整个扫描调用的样本以及实际读取统计。Java 执行样本和 native 状态样本各自统计，不相加估算 CPU 占比。

`ECO_ROW_INDEX_COST=true` 可单独测量固定混合方块调色板的首次行解码、其余冷行解码和热行查询：复制成本排除，4 轮预热、8 轮采样，每轮 32 个调色板。这个小探针只用于暴露索引成本，不能替代服务器 MSPT。该开关、代码与诊断注入均不进入发行 JAR。

最终 `eco-halo-final-release-20260907.log`：纯 Fabric 全部 21 项通过，三平台 native 构建及发行 JAR 构建成功，10:45:14 启动命令返回 0。`eco-halo-final-stack-20260907.log`：11 模组组合全部通过，含新版诊断注入的装载检查和行成本探针，10:51:39 返回 0；该次 `-Pparity` 不计压测时间。运行时验证仍仅为 Windows x64。

- 游戏 PID 72988，JFR 确认主世界线程 OS TID 28244。
- 测量 Unix 毫秒 `1788748945118..1788748996910`。
- ETL 开始于 UTC `2026-09-07 02:42:10.7776018`；对应截取相对 `14340398..66132398` 微秒。
- CPU 采样周期 1 ms，ETL 丢失事件/缓冲区均为 0。分母是所选窗口、进程和线程的全部 CPU 采样，不要求样本带完整调用栈。
- 辅助进程只负责 WPR 启停；10:44:00 正常结束，随后 `wpr -status` 确认没有录制。原始系统级 ETL 仅保留本地，不进入 Git 或发行 JAR。

### 同一 CPU 分母下的完整地址归类

后续已使用独立 JVMTI 地址映射重新完成 Java + native 联合采样，见 [JIT 地址解析报告](unified-cpu-jit-2026-09-07.md)。下面保留的是本轮没有 JIT 映射时的历史结果，不应用新一轮比例倒推旧地址。

上述 46,368 个样本中，还有未解析地址 31,779（68.54%）、`jvm.dll` 544（1.17%）、系统/驱动及其他运行库 1,356（2.92%）；加上本模组 DLL 的 12,689 个样本即全部样本。未解析地址包含动态代码，但不能仅凭未解析就全部标成某个 Java 方法。系统/驱动的采样还可能发生在中断上下文，不能直接认作模组自身执行逻辑。

因此，同一口径能够列出 native 排序、查询主体、推动段计算和以上未解析/运行库分类；**尚不能**将方块扫描、Java 写回、输入快照等细分到这个 CPU 分母。JFR 的 Java 执行样本分布不应按比例缩放后冒充 WPR 实测。要得到完整的 Java + native 方法级统一排名，还需要记录 JIT 代码地址、方法及其生命周期的对应关系。

同窗口 JFR 的 native 状态样本为 669 个，其中查询 523、推动段执行 141；这是另一个统计口径，不与上表相加。当前下一步目标应是减少重复排序工作，同时完整保留原版 section/插入顺序、即时更新和特殊推动边界，而不是截断候选或按密度换路径。本次尚未修改 native 排序算法。

复现解析：先以本次保留的 `D:\ar-profiles\eco-halo-native-symbols-20260907` 为 `_NT_SYMBOL_PATH`，用 xperf 的 `-symbols -a dumper` 导出 PerfInfo 与 Image provider；然后运行 `tools/profiling/NativeCpuSummary.ps1`，指定上述 PID/TID/相对窗口。脚本同时按加载地址范围核对 DLL，支持 C++ 模板符号中的逗号，输出逐 RVA 计数及按符号分组结果。实际导出及汇总为 `eco-halo-native-samples-20260907.csv`、`eco-halo-native-source-20260907.csv`。JFR 窗口/线程筛选由 `JfrWindowSummary.java` 完成。
