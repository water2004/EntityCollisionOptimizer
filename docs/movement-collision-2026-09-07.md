# 移动碰撞接管与扫描诊断（2026-09-07）

## 已实现范围

启用本模组时，服务端 `Entity.collide` 和两个 `collideBoundingBox` 入口直接进入本模组实现。普通移动和跨台阶共用有序稀疏扫描；不再执行 Lithium 对应的移动求解代码。轴裁剪和台阶候选高度仍调用 Minecraft 的几何函数，保留原版浮点运算和顺序。

非空气行位图附着于每个 `PalettedContainer<BlockState>`，按需扫描 16 个位置建立一行，已索引行随单格写入更新。容器反序列化清除索引，复制不共享索引。每个被索引容器的数组载荷为 512 字节位图加 32 字节有效标记，不包含对象头。没有全局方块缓存、全局锁或跨维度碰撞数据。

位图只是保守候选索引，不保存碰撞形状或实体状态。所有非空气候选按原版 z/y/x 顺序做 halo 过滤和实时形状查询。形状列表仍按实体、世界边界、方块排列；保持原版台阶判断和轴求解。没有引入密度分流、速度上限、候选数量上限或近似几何。

本次没有实现此前讨论的多项式/矩聚合实体推力近似求解，也没有把方块几何搬到 native；改进来自减少扫描工作量。实体推动继续使用现有 FFM 空间索引，Carpet 的数量规则不变。

## 原热点为什么大

接管前，两次带优化模组的诊断分别采集了 600 个测量 tick、600,000 次僵尸移动。初版诊断间隔为 64，最终改为与 1,000 互质的 67，避免固定 tick 顺序只抽到部分实体。

| 接管前模式 | 请求水平位移均值 | 样本实际水平位移 | 每次移动的跨台阶方块读取均值 |
| --- | ---: | ---: | ---: |
| 本模组开启 | 43.557 格 | 0 格 | 6,779.008 |
| 本模组关闭，优化模组保留 | 43.453 格 | 0 格 | 6,809.584 |

推力积累使请求位移远大于墙壁允许的实际位移。原版跨台阶逻辑仍以请求位移扩展扫描盒，因而每只僵尸会扫描数千个位置。按 1,000 只估算，仅这一步就有每 tick 约 680 万次方块状态读取。相对于实体数量的 O(n) 假设没有计入不断变化的每实体扫描体积。

Lithium 已替换正常移动扫描，但此版本的跨台阶形状收集仍进入原版 `BlockCollisions`。旧 JFR 中调色板、方块形状和迭代器的热点对应这条调用链。

## 接管后的首次诊断

`eco-owned-movement-scan-20260907`：600 个测量 tick，600,000 次移动，间隔 67，8,956 个样本。请求水平位移均值 43.478 格，没有缩短请求位移。

| 阶段 | 本模组扫描次数 | 原版扫描次数 | 每次采样移动的候选状态读取均值 |
| --- | ---: | ---: | ---: |
| 普通移动 | 8,956 | 0 | 116.837 |
| 跨台阶 | 8,714 | 0 | 128.298 |

两阶段合计约 245 次；候选扫描的空气读取为零。这里不包含首次建立位图的读取、碰撞上下文内部自行访问的方块和其他游戏系统的读取。各次独立生成的种群、抽样间隔及测试布局有差异，前后读取均值用于解释工作量，不应换算成同等比例的 MSPT 提升。

首次无扫描统计的接管后 JFR（`eco-owned-movement-initial-20260907.jfr`）中，`OrderedBlockColliders.Scan.run` 的叶子样本占 4.72%，形状处理 `Scan.add` 占 1.11%；主要叶子热点变为 `Integer` 装箱、`CollisionFrame.entity` 和 `Entity.push`。这是整个录制期的采样分布，既不是方法精确耗时，也不是互不重叠的完整子系统耗时。

## 性能对照口径

同一进程按 Vanilla/FFM/FFM/Vanilla（ABBA）顺序运行；每轮重建 1,000 只正常 AI/重力、生命一亿的僵尸和真实石质拥挤室。生存玩家持击退 II 钻石剑，每 13 tick 攻击。每轮预热 80 tick、测量 200 tick。各轮打印独立统计，汇总每模式 400 个样本。

关闭模式保留 Lithium 等优化模组；开启模式包含本模组已有实体优化和本次移动优化。因此百分比是本模组整体收益，不是这次方块修改的独立收益。

| 无扫描统计的独立运行 | 关闭均值 mspt | 开启均值 mspt | 均值降低 | 关闭/开启 p95 mspt |
| --- | ---: | ---: | ---: | ---: |
| `eco-owned-movement-abba-20260907`，初版接管 | 110.831 | 94.958 | 14.32% | 153.837 / 104.728 |
| `eco-owned-movement-abba-final-20260907`，按行惰性索引及完整入口接管 | 158.095 | 80.792 | 48.90% | 170.412 / 100.455 |
| `eco-owned-movement-abba-repeat-20260907`，相同最终实现复测 | 116.705 | 88.659 | 24.03% | 170.288 / 106.688 |

第二次运行的四轮均值依次为 163.144、67.479、94.106、153.047 mspt。自然拥挤种群的波动明显；不同运行之间还包含上述实现变化，不能把差额全部归因于它，也不能只挑最好的一轮作为稳定收益。

最终实现复测的四轮均值为 154.630、95.849、81.469、78.781 mspt。尤其末轮关闭模式明显变快，进一步说明种群状态对工作量的影响。最终实现两次汇总收益为 24.03% 和 48.90%，尚不能给出窄区间的稳定收益保证；每次只比较该次 ABBA 内的汇总。

最终诊断对照（`eco-owned-movement-scan-abba-final-20260907.log`）使用相同代码、间隔 67 的同轮 ABBA，每模式 400 tick / 400,000 次移动 / 5,971 个样本：

| 模式/阶段 | 每采样移动的候选状态读取 | 采样空气读取 / 全部候选读取 |
| --- | ---: | ---: |
| 关闭本模组：原版跨台阶扫描 | 6,452.077 | 37,746,256 / 38,525,350（约 98.0%） |
| 开启：普通移动 | 107.153 | 0 / 639,810 |
| 开启：跨台阶 | 113.190 | 0 / 675,860 |

开启后两阶段合计约 220 次候选读取。关闭模式的普通移动由 Lithium 自身扫描器处理，不在该读取统计内；零计数并非没有工作。两种模式仍是独立种群，本次请求位移均值分别为 42.313 / 37.413 格；差异不能被当成严格配对的几何工作量比较。诊断本身有开销，其 MSPT 不进入正式收益表。

早先未提交的方块状态缓存实验（`eco-direct-block-cache-20260907`）得到关闭 360.878、开启 413.203 mspt，未显示收益。该实验已经移除；并非发布版的自动回退路径。它与本次测试环境、时段和种群不同，不作为本次提速百分比的基准。

## 测试与兼容性

- 32,366 个已注册方块状态：与原版 `BlockCollisions` 比较返回形状的顺序及 AABB 列表。这是单个布局下的状态枚举，不代表全部布局和方块实体内部状态。
- 1,743 次移动/直接碰撞入口对照，包括 20 只僵尸和 4 艘船；开启模式另检查实际进入接管实现，防止测试只跑到原版路径。
- 360 次运动中活塞形状检查：六方向、伸出/收回、三种移动方块、五个进度，包含 halo 扫描。
- 32 步连续 `Entity.move`：位置、速度、落地/碰撞标志、落距。
- 行索引：所有行与原始调色板比对，三种单格写入、复制隔离、反序列化。
- 保留原有低/中密度实体推动、同帧状态失效、跨维度并发测试；新增五种推动后的速度观察测试。普通僵尸继承 `LivingEntity.push(Entity)` 的睡眠检查覆写，所以这些观察测试不能证明旧 native 冲量分支被覆盖。`60c5615` 的 native 冲量资格判断没有覆盖普通僵尸，这一缺口仍需独立修复和验证。

联合加载：Lithium 0.25.3+mc26.2、Carpet 26.2+v260906、FerriteCore 9.0.0、ServerCore 1.5.19、C2ME 0.4.2-alpha.0.43、VMP 0.2.0+beta.7.236、Krypton 0.3.1、Alternate Current 1.9.0、ScalableLux 0.3.0-alpha.0.3、Noisium 2.8.5+mc26.2-pre-2、Worldthreader 3.1.0。

纯 Fabric 环境和上述联合加载环境均通过全部 8 项 GameTest；最终 `build` 通过。发行包不包含 GameTest 类或诊断 mixin。没有声称测试了其他版本、全部方块实体内部状态或任意其他模组自定义碰撞。

## 复现

```powershell
./gradlew.bat runGameTest -Pparity
./gradlew.bat runGameTest -Pbenchmark -PcompatModsDir=<优化模组目录> -PjfrOutput=<输出.jfr>
```

诊断运行另设置 `ECO_SCAN_DIAGNOSTICS=true`；正式性能对照须取消该变量。`ECO_BENCHMARK_PROFILE=optimized` 或 `baseline` 将 ABBA 改为一个模式的 120 tick 预热和 600 tick 测量。原始 JFR 和日志保存在本机 `D:\ar-profiles`，不加入发布 JAR 或 Git。
