# Native 推动段执行与段末写回（2026-09-07）

## 执行边界

经用户确认，将连续普通推动段的速度计算也移入 native，整个段结束后写回。只验证低密度、中密度行为；所有密度使用同一算法，没有密度阈值、数量截断或失败回退。当前仍逐对执行，不是高密度近似聚合。

原实现是 native 计算冲量、Java 逐对调用 `Entity.push`；现在的流程是：

1. 沿既有原版候选顺序划分连续普通推动段。挤压伤害仍在推动之前；特殊原版推动保持原来的调用位置。
2. 每段开始读取来源与目标的实时位置、速度、推动条件。速度 getter/setter 有覆写时不认作可直接执行的普通段。只承诺原版实体和已测试的优化模组，不声称能识别其他模组向既有方法体注入的任意副作用。
3. 一次 FFM 调用执行整段：每对先目标后来源，来源速度严格逐次相加，不先汇总冲量。禁止浮点乘加融合，保留负零、输入非有限拒绝、结果非有限拒绝及 `needsSync` 语义。
4. 段末逐个写回真实速度和同步标志，再返回调用者或执行下一个特殊推动；下一段重新读取输入。数值数组仅为当前调用的工作区，没有跨 tick 的权威速度镜像，也不修改 getter 来物化结果。

状态筛选复用原有实体/方块版本失效缓存，将可推动性、载客、乘客、睡眠编码在一个状态值中。睡眠数据变更使该缓存失效，删除原先独立的睡眠缓存接口；`noPhysics` 仍读取实时字段。只有存在乘客关系时才需要比较根载具；不同的非乘客实体不可能共享根载具。没有新增生产 Mixin 或按模组名称的补丁。

每段目标唯一，来源不在目标列表内；该不变量由候选去重与过滤保证。目标通常仍需一次 `Vec3` 写回，主要减少的是同一来源在段内的多次对象创建。快照传输变大，因此 native 化本身不保证性能提升。

删除旧的 `calculatePushImpulses` 导出、Java 入口和仅为冲量准备的两块缓冲区；225 对数值边界测试及连续累加测试也直接使用新的 `executePushRun`。不保留第二套旧 API。

## 正确性验证

- 原有全部低、中密度交互对照保留，包括实体推动、玩家、物品、点燃 TNT、末影珍珠、风弹、活塞、蜂蜜、流体、异形方块、机器通道和三维度并发隔离。
- 新增 90 组：实体总数 2/8/20，6 种初始速度，5 种状态组合。用真正 `target.push(source)` 得到预期，再验证整段一次写回、拆成两段分别写回，逐位比较所有真实速度字段及同步标志。
- 初始速度覆盖负零、普通值、大数舍入、最大有限值，以及测试访问器人为写入的 NaN/Infinity。非有限原始状态仅用于检查拒绝规则，不代表有效的原版世界状态或自定义实体兼容承诺。
- 候选收集后再改变目标睡眠/`noPhysics` 或来源生命值，确保执行阶段没有沿用收集前的状态。
- 测试专用观察器注入真正 `AbstractBoat.push(Entity)` 的入口，验证普通僵尸、船、普通僵尸交错时，船回调读到的真实字段和原版相同。观察器不修改行为，也不进入发行 JAR。
- 三维度并发测试经 `PushBatch.applyNativeRun` 执行 4,500 个完整 native 推动段，验证跨维度数据及缓冲区隔离。

对照不是只比最终速度：新增用例检查各段的提交边界；但不保证无同步的其他线程能够逐对观察段内部的中间速度。

## 测量方法

Minecraft 26.2、Java 25.0.2、Windows x64，加载与 [兼容性记录](compatibility-parity-2026-09-07.md) 相同的 11 个优化模组。1,000 正常 AI/重力僵尸，生命一亿，真实石室与生存玩家击退 II 剑。单模式 120 tick 预热、600 tick 测量；开启 JFR，不开 WPR 或扫描统计。每次独立启动和重建自然种群，不以单次差额声称统计显著。

原始日志/JFR 在 `D:\ar-profiles`，不打入发行 JAR。使用 `tools/profiling/JfrWindowSummary.java` 按各日志的测量起止毫秒和 `worldthreader_minecraft:overworld` 筛选，区分 Java 执行样本、native 状态样本和分配抽样权重；它们不是可相加的 CPU 耗时。

第一次实现的完整测量为 71.236 MSPT，修改前为 65.405，慢约 8.9%。同一窗口的 `Vec3` 分配抽样权重由 32,651.51 MiB 降到 17,923.50 MiB（约 45.1%），但准备/写回成本抵消了收益。JFR 中睡眠状态读取为 17.64% 的 Java 叶子样本，写回为 16.99%；随后才将推动状态合并进现有失效缓存，没有把“分配减少”当成“服务器一定更快”。后续结果见下方最终测量。

## 最终测量与结论

以下均开启本模组，不是本模组开/关收益对比。日志和 JFR 共用表中的文件名前缀，后缀均为 `-20260907`。

| 实现 / 文件名前缀 | 平均 MSPT | 中位 | p95 | Vec3 分配抽样权重 MiB |
| --- | ---: | ---: | ---: | ---: |
| 修改前 / `eco-run-writeback-before` | 65.405 | 64.332 | 74.302 | 32,651.51 |
| 初版段末写回 / `eco-run-writeback-after-retry` | 71.236 | 69.718 | 81.489 | 17,923.50 |
| 合并状态缓存 / `eco-run-writeback-packed` | 61.906 | 60.990 | 71.084 | 16,262.75 |
| 合并状态缓存独立复测 / `eco-run-writeback-confirm` | 67.388 | 66.377 | 75.334 | 17,223.27 |

最终两次相对修改前分别约快 5.3%、慢 3.0%，不足以证明稳定的 MSPT 改善。`Vec3` 分配抽样权重减少约 47–50%；这支持减少来源速度对象创建的判断，不是精确分配字节计量。每次均攻击 55 次，但自然运行中的有效攻击/可观察击退分别为 10/14/12/16 次，不能把不同随机演化的高密度种群当作完全相同的逐 tick 输入。本轮没有将高密度自然误差或单次性能波动归为低、中密度等价性证据。

最终独立复测测量窗口 `1788746816057..1788746856610`，主世界维度线程有 1,889 个 Java 执行样本：

- 最近的本模组调用者为方块扫描 `Scan`：400（21.18%）；其中调色板取值占 385 个 Java 叶子样本（20.38%）。
- 段末写回 `commit`：349（18.48%），其中自身叶子样本 321（16.99%）。
- 速度快照准备 `capture`：173（9.16%）；`applyNativeRun` 自身附近仍有 128（6.78%）。
- 候选收集 `collectPushable`：116（6.14%）；FFM 推动执行入口：70（3.71%）。

另有 479 个 native 状态样本，其中候选查询 358、推动段执行 116，剩余 5 个为分配/帧更新等调用。这里只能定位采样时位于哪个 FFM 调用，不能将它们换算成 native 内部函数耗时或与上面的 Java 百分比相加。native 推动执行不是“没有被采到”，也不能由这一分布认定它比 Java 查询占用更多 CPU。

结论：整段 native 执行和段末真实写回已实现，分配压力下降；MSPT 收益尚未证明。当前仍值得关注的成本是方块扫描、目标写回/输入准备和 native 候选查询，不应继续仅凭 native 化方向猜测收益。

## 最终验证与产物

- 清理旧 API 后，`runGameTest build -Pparity --no-daemon` 和包含 11 个优化模组的 `runGameTest -Pparity ... --no-daemon` 都通过 21 个测试入口并自行退出。21 项由 19 项行为/隔离测试、1 项压测入口及 Minecraft 的 `always_pass` 组成；`-Pparity` 下压测入口跳过计时，不将其算作性能样本。
- 上表各有效 profile 都完整执行其压测；新实现的三次有效 profile 均完成全部 21 项。被手动中断且 JFR 为空的样本已排除。
- 性能采样在删除不再调用的旧冲量 API/缓冲区之前；删除后仅重跑完整行为测试和构建，没有为该清理操作声称额外性能收益。
- 发行 JAR 包含 Windows/Linux/macOS x64 native 库，不包含 GameTest、边界观察器、旧睡眠接口或 PDB。三平台构建成功；本轮运行时等价性、退出和性能验证仅在 Windows x64 进行。
- Windows 性能计数器/OSHI 警告，以及从优化组合切回纯环境时测试存档残留的 Worldthreader 规则读取告警，与“全部测试通过并成功退出”分开记录；没有把日志中不存在错误作为验收条件，也没有压制这些日志。
