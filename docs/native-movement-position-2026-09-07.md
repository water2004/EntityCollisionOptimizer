# Native 移动求解与位置权威（2026-09-07）

## 本轮边界

这轮把移动碰撞的数值求解迁入 native，并将已绑定服务端实体的完整位置放进共享状态表。不是把整个 `Entity.move`、`LivingEntity.travel` 或世界 tick 搬进 native，也没有取得端到端净提速的证据。

- `collision_body.h` 的共享行从 64 扩为 80 字节，保留原有推动字段偏移，追加 Y（64）与位置版本（72）。X/Z、速度及 needsSync 的偏移不变。
- 绑定后，位置字段的全部普通读取与写入（包含合并后的访问器、Carpet 方法）统一路由到表；Java 原字段只用于未绑定实体及解绑时物化。完整 `Vec3` 按版本缓存，不存在 Java/native 两份同时生效的位置。Java 的合法位置写入也写同一共享行。
- `Entity.collide`、两个 `collideBoundingBox` 和 `Entity.move` 中的碰撞求解调用进入同一个 native 求解器。原版顺序的 Y/X/Z 或 Y/Z/X 裁剪、体素索引、epsilon、台阶候选高度、float 转换和首次改善候选选择都在 native。数值运算关闭 FMA 融合。
- `Entity.move` 的数值目标位置在 native 中计算，但只在原来的位置提交点发布。原版提交阈值、摔落射线、轨迹记录、`setPosRaw` 的区块/世界通知、AABB 更新及后续回调时序保留；纯碰撞查询不移动实体。事务局部变量由 `@Share` 保持，不使用实体上的“上次移动”缓存，因此嵌套调用不会覆盖外层事务。意外中途改位会显式报契约错误，不回退。
- 无碰撞的 `noPhysics` 原版移动分支、活塞限位、潜行退边、重力/空气运动、碰撞后速度响应、摩擦/方块效果仍有 Java 逻辑。不能宣称整个移动过程已不需要 Java `Vec3`。
- 世界扫描和动态碰撞上下文仍由 Java 提供。`VoxelShape` 只缓存该不可变形状自身的坐标网格和占用位，不缓存“某个世界位置、某个实体应该得到什么形状”。移动/台阶各自在原版需要时重新收集上下文形状。每条形状引用附带平移量，native 按“坐标加平移”求值，避免用“查询减平移”造成远坐标舍入差异。保留完整体素，不以外接 AABB 替代异形方块。
- 普通完整方块不再逐次生成平移后的 `VoxelShape`；Java 列表收集与 native 引用收集共用原来的扫描器。native 几何缓存按形状生命周期回收，查询引用显式保持底层内存存活。
- 移动包和形状引用缓冲区按线程借还，嵌套层有独立租借，不按密度分流。稳定容量下不逐次申请/释放 native 内存。解除租借会清空形状强引用，避免池永久留住临时形状。实体不保存可能随表扩容失效的裸 row 指针；在同步 native 调用前、世界形状回调之后获取当前 row。
- 保持既有显式关闭/Carpet 推动所有权交接：释放 body 绑定时物化最新位置、速度与同步状态。移动求解的启用仍独立于 Carpet 的推动上限。因此这里的位置权威承诺是“已绑定实体”，不是强行给所有未跟踪/已移除实体、客户端或显式原版模式保留 native 所有权。

没有新增密度阈值、候选上限、近似截断、失败回退或按优化模组分叉的求解器。

- 在 32,366 个方块状态枚举期间，针对 6,114 个不同形状做 **495,234 次逐位位移对照**。oracle 是未被替换的实际 `Entity.collideWithShapes`，不是重写一份 Java 算法。覆盖三个平移范围（含近三千万坐标）、穿入/侧碰/落地、两个水平轴优先级及微小位移。

这些是采样估计，不是精确分配计数。总权重约下降 67.7%，Vec3 约下降 **17.8%**；主要减少的是临时形状和坐标包装，不能把总分配降幅当成 Vec3 降幅或 CPU 提升。

native 的裁剪/台阶循环不创建 Java Vec3。初稿的三个提前物化向量已改成一个必需的位移结果；只有原版判定要提交位置时才构造目标 Vec3，起点读取复用原版位置对象。纯查询不构造起终点结果。

最终 Vec3 分配采样中，本模组位移结果约 31.99 MiB。其余仍主要来自 Java 的空气运动/重力、`restituteMovementAfterCollisions`、方块效果路径、历史位置/速度计算、AI 视线和速度观察边界。若要进一步接近消除，需要继续迁移这些连续的数值更新段，而不仅仅移动位置存储。最终还有 `NativeMovement.Result` 等 Java 桥接对象，尚未消除。
