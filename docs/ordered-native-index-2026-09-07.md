# native 有序候选索引与验证（2026-09-07）

本阶段完成了“消除逐来源重复排序”。位置的事件驱动共享镜像、候选 ID 留在 native、推动循环进一步批量化尚未实施，避免把多个改动混入本轮热点验证。

## 实现与边界

- `CellMembers` 持有成员 ID 和 `orderDirty`。只有成员插入/移除、section 坐标或 section 插入顺序变化才使有序成员失效；生命、队伍等语义状态刷新不使排序失效。
- `OrderedCandidates` 对脏单元按原版 section 键和插入顺序排序，然后用当前维度自己的游标堆合并所涉单元。全序中的重复 ID 相邻，因此只返回一次。查询在有序流上实时执行原有 AABB、section、语义状态及队伍筛选，不再对每个来源的结果重新排序。
- 原版 section 键顺序仍为有符号 X、打包后的无符号 Z/Y，再按 section 内插入顺序。未补齐元数据时可能临时出现相同排序键，用 ID 提供确定全序；补齐排序键会使相关单元失效，在正式结果返回前重新排序。
- 空间索引每帧重建时清除缓存；这里是帧内复用，不声称完全消除所有排序。跨单元移动、section 出入/再进入、新增、移除及网格重建均保留失效语义。
- 没有新增 Java 注入、native ABI 变更、密度分流、候选截断或失败回退。所有密度使用同一套合并算法。特殊实体回调、挤压伤害和速度观察边界不变。
- 维护成本只在相关结构变化后发生；查询合并成本取决于所涉单元数及其成员数。高速跨单元运动仍可能频繁失效，本次石室场景的收益不是对所有空间分布的保证。

新增生产实现集中在 `native/src/ordered_candidates.{h,cpp}`；上下文、空间成员和元数据入口只负责失效通知，查询入口只负责消费有序流，没有按实体种类或模组增加特判。

## 验证

纯 Fabric 和完整 11 优化模组组合均通过 **23 项 GameTest**，Windows 游戏进程正常退出。保留全部既有实体/方块/玩家/机械交互、速度逐位、同步状态、特殊回调及三维度并发测试。

新增：

- `OrderedCandidateParity`：2/8/20 个真实实体，1,530 次候选列表对照，以原版世界实体查询的实际返回顺序为 oracle。覆盖跨 native 单元、跨 Minecraft section、移出再进入、重复查询复用、帧内新增/移除和下一帧重建。
- `NativeOrderChecks`：2/8/20 个实体状态、96 个变化阶段、8,640 组查询对照（元数据重试另计），使用 Java 的 `SectionPos.asLong` 排序键作为独立参考。覆盖负坐标键、排序键变化但单元成员不变、多个单元中的重复 ID、可选中/乘客变化、全局元数据失效、元数据补齐、网格重建；逐项检查 ID 顺序、计数、body slot 与 native 分派标志。
- Windows/Linux/macOS x64 原生库构建成功；运行验证平台是 Windows x64。发布 JAR 含三平台库，不含测试、JIT agent、PDB 或客户端专用注入。

## 同一 CPU 口径：排序没有仅仅转移成合并开销

基线直接使用此前已经采集的 [当前热点报告](current-unified-hotspots-2026-09-07.md)，未重跑旧实现。改后仍为 1,000 普通 AI/重力僵尸、1 亿生命、真实 1×2×1 石室、生存玩家击退 II 钻石剑，加载同一组 11 优化模组；120 tick 预热、600 tick 测量。

## 剩余热点

同一改后线程分母下，native 查询主体 **18.04%**、Java 方块扫描及内联区块访问 **15.71%**、Java 绑定检查/位置准备 **12.75%**、native 推动 **12.65%**、native 合并 **3.93%**。

排序已不是下一步重点。候选筛选仍逐来源执行，Java 仍逐目标检查共享表绑定/位置，候选槽位仍往返拷贝。后续应围绕这些已确认的热点继续减少重复处理；不能把方块扫描的样本全部当成碰撞箱数学计算，也不凭本次函数级采样断言平方根或缓存未命中是瓶颈。
