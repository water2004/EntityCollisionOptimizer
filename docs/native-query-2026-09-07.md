# native 查询循环优化（2026-09-07）

本轮针对上一阶段 `queryPushableEntities` 的 **3,951 / 18.04%** 全线程 CPU 样本。基线复用 [有序索引记录](ordered-native-index-2026-09-07.md) 对应的已采集数据，没有重跑旧实现。

## 从采样定位到实际改动

匹配上一轮 DLL/PDB 的地址采样与反汇编显示，查询候选循环内反复执行来源 AABB 的六个 section 边界计算，包含浮点取整、转换和范围比较；查询结束后又遍历结果，重新读取同一批元数据以填 body slot 与分派标志。它们不是 native 调用入口的虚拟归因：采样地址落在实际循环代码中。

本轮改动：

1. `LookupSections` 保存来源的六个整数边界，每次查询只计算一次。来源 AABB 按值保存、来源 native 推动能力也在循环前读取，查询循环只读取目标状态。
2. 结果缓冲区由“头、ID[size]、slot[size]”改成“头、ID[capacity]、slot[capacity]”。总分配大小不变，固定的 slot 起点允许筛选通过时一起填 ID、slot 和 native 标志，删除第二次元数据遍历。Java FFM 读取端同步使用 capacity 偏移。
3. 保留全部 AABB、section、可选中状态、队伍筛选及计数；有序合并、失效机制、元数据补齐协议、特殊实体回调和推动计算均不变。空/不可索引来源仍返回空结果，不把 NaN/Inf 边界转换为整数。

这是同一路径的重复计算消除，没有密度阈值、候选截断、行为近似或静默回退。没有新增 Mixin 或注入目标。内部查询缓冲区约定与打包在同一 JAR 内的 Java/native 两端一起更新，导出函数参数和共享实体状态表布局不变。候选 ID 的 Java/native 往返、位置准备循环尚未删除。

## 边界测试发现并修复的问题

新增的原版 `SectionPos.posToSectionCoord` 对照在第一轮失败：`phase=30 rule=0 native=false`，期望候选 `[4]`，实际 `[2,4]`。

原因是此前用 `floor(value / 16)` 计算 section。对于 `Math.nextDown(0.0)`（最接近 0 的负 double），除以 16 下溢成负零，从而得到 section 0；原版先 `Mth.floor(value)` 得到 block -1，再右移 4 位，得到 section -1。原版 `EntitySectionStorage` 的查询使用后一种顺序。

生产实现统一改为先对 block 坐标向下取整，再右移 4 位，没有对零、实体类型或密度加特判。失败用例保留，未放宽断言。范围针对当前支持的原版世界坐标，不声称支持任意超出 Minecraft 坐标域的第三方实体数据。

当前最大单项是 Java 方块扫描及内联区块访问 **16.33%**，之后为 native 查询主体 **14.75%**、native 推动 **13.67%**、Java 绑定检查/位置准备 **12.87%**。查询并未消失，加上合并和排序仍占 **19.67%**。
